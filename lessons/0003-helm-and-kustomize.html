Helm and Kustomize

Lesson 3 of your CKAD prep. About 10 minutes, then run session-02.

1. Two ways to avoid copying YAML

Both tools turn one set of YAML into many variants. They differ in how:

  • Helm fills in a template. A chart is a folder of templates with default values. Installing a chart creates a release, and every install, upgrade or rollback adds a numbered revision to that release.
  • Kustomize edits plain YAML. A base is ordinary manifests plus a kustomization.yaml. An overlay is another kustomization.yaml that points at the base and lists changes. It is built into kubectl.

The exam lets you open helm.sh/docs as well as kubernetes.io.

2. Helm: the release lifecycle

helm show values ./chart                  # what can I set?
helm install shop ./chart --set replicaCount=2 --set image.tag=1.27
helm install shop ./chart -f my-values.yaml  # same, from a file
helm list -A                              # every release, every namespace
helm upgrade shop ./chart --set image.tag=1.28
helm history shop                         # revisions and what each did
helm rollback shop 1                      # no number = the previous revision
helm uninstall shop

Every command works on the current namespace. Add -n <ns> as you would with kubectl. Release names are only unique within a namespace, so helm list without -A can miss the one you are looking for.

A rollback doesn't delete the bad revision. It adds a new revision that copies the old one, so after rolling back from 2 to 1, helm history shows revision 3 with the description Rollback to 1.

On the exam the chart usually comes from a repository: helm repo add <name> <url>, helm repo update, helm search repo <name>, then helm install <release> <name>/<chart>. Your practice tasks use the local chart charts/web, so they work offline.

3. Kustomize: base and overlay

prod/kustomization.yaml
resources:
- ../base               # the base folder, not a file
namespace: prod
namePrefix: prod-       # web becomes prod-web
labels:
- pairs:
    env: prod
images:
- name: nginx           # the image name in the base
  newTag: "1.27"
patches:                # anything else: a partial object
- patch: |-
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: web         # the name in the base, before the prefix
    spec:
      replicas: 3

Preview with kubectl kustomize prod/, then apply with kubectl apply -k prod/. Previewing first catches most mistakes, because the output is the exact YAML that will be applied.

Two field notes. labels adds labels to the objects but leaves selectors alone. commonLabels also rewrites selectors, which breaks an existing Deployment, because its selector can't be changed. In a patch, name the object as the base names it, without the prefix. To change only the replica count, a replicas: list (- name: web and count: 3) replaces the patch.

The docs page is Declarative Management of Kubernetes Objects Using Kustomize. Search it for Bases and Overlays and for the field table.
