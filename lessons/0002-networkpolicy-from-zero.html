NetworkPolicy from zero

Lesson 2 of your CKAD prep. About 10 minutes, then retry the two tasks diag-01 missed.

1. The one idea

By default every Pod accepts traffic from every other Pod. A NetworkPolicy changes that for the Pods it selects. Once a policy selects a Pod for incoming traffic, the Pod accepts only what some rule allows and drops everything else. Pods that no policy selects stay open.

So a NetworkPolicy is an allow list. You never write "block X". You pick Pods, and anything you don't allow for them is blocked. If two policies select the same Pod, it accepts what either one allows.

2. Read one, line by line

This policy lets Pods labelled app=web accept traffic only from Pods labelled app=frontend, on TCP port 8080:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-allow
spec:
  podSelector:            # WHICH Pods this policy protects
    matchLabels:
      app: web
  policyTypes:
  - Ingress               # it controls incoming traffic
  ingress:                # list of allow rules
  - from:                 # rule 1: WHO may connect
    - podSelector:
        matchLabels:
          app: frontend
    ports:                # rule 1: ON WHICH port
    - protocol: TCP
      port: 8080

Read it as two questions. spec.podSelector answers "who is protected?". Each item under ingress answers "who may come in, and on which ports?". A podSelector inside from matches Pods in the policy's own namespace.

Two shapes to recognise:

  • podSelector: {} selects every Pod in the namespace.
  • policyTypes: [Ingress] with no ingress list allows nothing in. That is the "default deny" policy.

3. The trap: one dash or two

Inside from, each dash starts a separate source, and the sources are OR-ed. Two selectors under one dash are AND-ed.

# OR: Pods labelled app=frontend in this namespace,
#     OR any Pod in namespaces labelled team=a
  - from:
    - podSelector: {matchLabels: {app: frontend}}
    - namespaceSelector: {matchLabels: {team: a}}

# AND: Pods labelled app=frontend that are in namespaces labelled team=a
  - from:
    - podSelector: {matchLabels: {app: frontend}}
      namespaceSelector: {matchLabels: {team: a}}

The only difference is the dash before namespaceSelector. Exam tasks test this.

4. How to write one fast

kubectl create has no NetworkPolicy generator, so copy the example from the docs. Open Network Policies and copy the "test-network-policy" YAML (search the page for test-network-policy). Delete what you don't need: egress, ipBlock, namespaceSelector.

  1. Look at the labels first: k get pods --show-labels.
  2. Paste the docs example into np.yaml, then trim it and fix the names, labels and port.
  3. k apply -f np.yaml, then k describe netpol <name>. The describe output says in plain English who is allowed in.

Your Docker Desktop cluster does not enforce NetworkPolicies, so traffic tests won't prove anything here. Trust describe and the checker.

5. Check yourself

A policy selects app=db and allows ingress only from app=api. Can app=other still receive traffic from anyone?

What does this policy do? podSelector: {}, policyTypes: [Ingress], no ingress field.

Under from: - podSelector: {app: api} and - namespaceSelector: {team: a}, each with its own dash. Who may connect?

6. The sidecar you missed

Two separate mistakes broke native-sidecar.

A shell loop needs a shell. while true; do ...; done is shell syntax, not a program. Give the container command: ["sh", "-c", "while true; do ...; done"]. With kubectl run, the end of the line is --command -- sh -c '...'. If the container is in CrashLoopBackOff, k logs <pod> -c <container> and k describe pod tell you why.

A native sidecar is an init container with restartPolicy: Always. A second entry under containers is an ordinary container. It has no start order and no sidecar behaviour. The native sidecar goes under initContainers:

spec:
  initContainers:
  - name: shipper
    image: busybox:1.36
    restartPolicy: Always    # this line makes it a sidecar
    command: [...]
  containers:
  - name: main
    ...

It starts before the main containers and runs until the Pod stops. The docs page is Sidecar containers.
